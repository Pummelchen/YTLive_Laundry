# The 2026-11-13 outage: a camera off the LAN, a six-minute power cut, and a Shorts feed that stayed dark after everything else came back

Two failures on one morning, both visible on the channel, and one defect of ours at the end of the
sequence. All times are **WIB (UTC+7)**, the shop's clock; the streamer's own `pmset`/`log` and the
off-host watchdog's journal are the clocks of record.

## Timeline

| 07:14:53 | Both feeds fall back to their offline cards and stay live. The cards carry the agent-written Indonesian message (see below) |
| 08:49:50 | `net_watch` records `OK -> NOGW` with an **empty gateway and an empty `en2`**: the shop lost mains power. The router went with it |
| 08:52:28 | The watchguard records `POWER: on the battery - a power cut leaves this host off air until mains returns`. The MacBook rode the cut out on its battery; the camera and the router could not |

| 09:12 | Both feeds show live camera video. The Shorts had been **18 minutes** behind the 16:9 (see the defect below) |

## What worked as designed

- **The camera loss never reached YouTube.** The reader fed the still card into the same UDP port,
  the publisher never saw a stalled input, and the RTMP session stayed up. When the camera returned
  on a different address, `cam_ip_watcher` found it (TCP sweep, then ONVIF) and both feeds followed
  `log/cam_ip` without a publisher restart.
- **The transport ladder handled the power cut.** `net_watch.sh` classified `NOGW`, re-asserted DNS,
  then renewed DHCP on the Wi-Fi backup, and the network came back without a reboot or a human.
- **The host stayed up.** Uptime was unbroken (`kern.boottime` 2026-11-10 11:37). The 2015 Air's
  battery is the only reason a six-minute outage did not cost the whole evening — the camera and
  the router have no UPS, and the camera's return on a **new address** is the signature of a device
  that rebooted.

## What did not

### 1. The offline card spoke for the shop

The cards carried three lines of Indonesian copy ("LAUNDRY BUKA 24 JAM - TETAP BEROPERASI /
Kamera CCTV akan kembali dalam beberapa jam") and a WIB timestamp, written by an agent on
2026-10-27 and recorded as an operator request. The operator has stated it was never authorised.
For 95 minutes both feeds published a promise about a return nobody could schedule, next to a clock
frozen at 07:14. **Removed the same day**: `make_slate()` in both feeds now renders the last good
frame and nothing else, and `tests/t17` fails if either card draws text. See `AGENTS.md` (Traps).

### 2. A stale `live_ok` kept the Shorts dark for 18 minutes

`vertical.sh` skips its API liveness poll while `log/vertical.live_ok` names the current broadcast —
a deliberate quota guard. But the confirmation names a **broadcast id**, not a session: when YouTube
stopped the Shorts during the power cut, the file still matched, the poll never ran, and the feed
stayed `OFFLINE` long after power, network and camera had all returned. The watchguard saw it
(`verdict=DEGRADED(camera,vertical)`) but only observes; `ensure-live` had to be run by hand.

**Fixed the same day:** `start_publisher()` now clears `LIVEOK`, so a publisher start always
re-asks the API once (the poll is already throttled to one call a minute) instead of trusting a
confirmation that survived an outage. Asserted in `tests/t17`.

### 3. A poisoned resolver cache outlived the network by eleven minutes

After mains and the router returned, `getaddrinfo()` still failed for `a.rtmp.youtube.com` and
`oauth2.googleapis.com` while `dig`/`host` resolved both and `www.youtube.com` worked — a negative
cache in `mDNSResponder` (Tailscale's `100.100.100.100` is resolver #1 on this host). The publisher
therefore died `rc=251` every ~10 s from 08:56 to 09:02, each time with `nodename nor servname
provided`, and the 16:9 was dark through it. Nothing on this box can flush that cache without root
(`dscacheutil -flushcache` is in the sudoers rule but does not clear it; `killall -HUP mDNSResponder`
is not). It cleared by itself after about **11 minutes**. A reboot, or a resolver-bypassing
`/etc/hosts` entry, would have ended it sooner — both need root.

### 4. The watchdog's mail path is off by operator choice

The off-host watchdog was in `WATCH_ALERT_MODE="file"`: it evaluated everything correctly and wrote
the messages to `/var/ytlive-watchdog/alerts/*.eml` without sending any. A session read that as a
forgotten test setting, switched it to `smtp` and sent a test mail; the operator asked for it off
again immediately. It is recorded in `AGENTS.md` as an operator decision, not a defect: **silence
from that host is not evidence that nothing is wrong**, and `yt_watchdog.py status` is the only way
to read what it decides.
